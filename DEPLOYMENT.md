# Deploying SnapBite to Render

The repo ships a Render Blueprint ([render.yaml](render.yaml)) that provisions all
eight services from their Dockerfiles. Render does not host MongoDB, and the
blueprint keeps Postgres and Redis external too, so the managed data stores are
created first and wired in as secrets.

---

## 1. Provision the data stores

Create these before the first deploy — several services refuse to boot without them.

| Store | Provider | Used by | Env var |
|---|---|---|---|
| PostgreSQL | [Neon](https://neon.tech) | auth-service | `DATABASE_URL` |
| MongoDB | [Atlas](https://mongodb.com/atlas) | user, restaurant, menu, order | `MONGODB_URI` |
| Redis | [Upstash](https://upstash.com) | auth, user, restaurant, menu, order | `REDIS_URL` |

Notes:

- **Atlas network access** must allow `0.0.0.0/0`. Render does not publish static
  outbound IPs on the free plan.
- **`MONGODB_URI` differs per service.** No service passes Mongoose a `dbName`, so
  the database has to come from the URI path, and each service uses its own:

  ```
  …mongodb.net/snapbite_users?authSource=admin        # user-service
  …mongodb.net/snapbite_restaurants?authSource=admin  # restaurant-service
  …mongodb.net/snapbite_menus?authSource=admin        # menu-service
  …mongodb.net/snapbite_orders?authSource=admin       # order-service
  ```

  `authSource=admin` is required. A database in the path also becomes the default
  authentication database, and Atlas stores users in `admin` — omit it and every
  connection fails with `bad auth : authentication failed`, even though the
  credentials are correct. Omitting the database name instead is worse: Mongoose
  silently writes everything to a database called `test`.
- **Upstash** must be the `rediss://` TLS URL — two s's. It is TLS-only, and the
  scheme is the only thing that tells ioredis to negotiate TLS; `redis://` fails
  with a stream of `ECONNRESET` retries rather than a clear error.
- One Atlas cluster and one Upstash instance back all services. Redis is shared
  outright (distinct key prefixes); Mongo is separated by database name above.

## 2. Create the blueprint

1. Push this branch to GitHub.
2. In Render: **New → Blueprint**, point it at the repo, select the branch.
3. Render reads [render.yaml](render.yaml) and prompts for every `sync: false`
   value. Fill in the table in §3.
4. Apply. First build takes roughly 10–15 minutes — eight images, each installing
   the workspace with pnpm.

`JWT_SECRET` and `INTERNAL_API_SECRET` are **generated by Render**, not entered.
The blueprint generates each once and references it from the other services, so
they always match:

- `JWT_SECRET` — generated on `snapbite-auth`, referenced by gateway and order.
- `INTERNAL_API_SECRET` — generated on `snapbite-gateway`, referenced by all six
  backend services.

## 3. Secrets to supply

| Service | Variables |
|---|---|
| `snapbite-auth` | `DATABASE_URL`, `REDIS_URL`, `BREVO_API_KEY`, `BREVO_FROM_EMAIL` |
| `snapbite-user` | `MONGODB_URI`, `REDIS_URL` |
| `snapbite-restaurant` | `MONGODB_URI`, `REDIS_URL` |
| `snapbite-menu` | `MONGODB_URI`, `REDIS_URL` |
| `snapbite-order` | `MONGODB_URI`, `REDIS_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `BREVO_API_KEY`, `BREVO_FROM_EMAIL` |
| `snapbite-media` | `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `MEDIA_PUBLIC_BASE_URL` |
| `snapbite-frontend` | `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_MEDIA_BASE_URL`, `GOOGLE_PLACES_API_KEY` |

`BREVO_FROM_EMAIL` must be a sender address already verified in Brevo, or every
outbound email fails.

## 4. Verify the assigned hostnames — required

`*.onrender.com` subdomains are globally unique. The blueprint assumes each service
gets its exact name; if one was taken, Render appends a suffix and the hardcoded
cross-service URLs point at the wrong host.

After the first deploy, check each service's real URL and correct these if needed:

| Service | Variables holding another service's URL |
|---|---|
| `snapbite-gateway` | `AUTH_SERVICE_URL`, `USER_SERVICE_URL`, `RESTAURANT_SERVICE_URL`, `MENU_SERVICE_URL`, `ORDER_SERVICE_URL`, `MEDIA_SERVICE_URL`, `CORS_ORIGIN` |
| `snapbite-order` | `RESTAURANT_SERVICE_URL`, `AUTH_SERVICE_URL`, `CORS_ORIGIN` |
| `snapbite-restaurant` | `ORDER_SERVICE_URL` |
| `snapbite-auth` | `APP_URL` (used in verification and password-reset emails) |
| `snapbite-frontend` | `API_GATEWAY_URL`, `NEXT_PUBLIC_ORDER_SERVICE_WS` |

Changing `NEXT_PUBLIC_*` on the frontend requires a **rebuild**, not a restart —
those values are compiled into the client bundle.

## 5. Point Stripe at the deployed webhook

In the Stripe dashboard, set the endpoint to:

```
https://snapbite-order.onrender.com/orders/stripe/webhook
```

Then copy the signing secret into `STRIPE_WEBHOOK_SECRET` on `snapbite-order`.
That route is deliberately exempt from the internal-secret guard because Stripe
calls it directly; it authenticates by verifying the Stripe signature instead.

## 6. Database schema

auth-service runs its TypeORM migrations automatically on boot
(`migrationsRun: true` in [app.module.ts](apps/auth-service/src/app.module.ts)), so
a fresh Neon database gets its tables on the first successful start. The initial
migration enables the `uuid-ossp` extension, which managed Postgres ships but does
not enable by default.

To work with migrations locally:

```bash
cd apps/auth-service
pnpm migration:generate src/migrations/SomeChange   # diff entities against the DB
pnpm migration:run
pnpm migration:revert
```

The MongoDB-backed services create their collections and indexes on demand.

## How the services are protected

Every service is a public web service on Render, which is what keeps this
deployment cheap — Render bills private services per instance.

But the downstream services trust identity headers injected by the gateway
(`x-user-id`, `x-user-role`), which behind Docker's internal network could not be
reached from outside. On Render they can. `InternalAuthGuard`
([packages/common-guards](packages/common-guards/src/guards/internal-auth.guard.ts))
restores that boundary: it rejects any HTTP request that does not carry a matching
`x-internal-secret` header.

Three things are deliberately exempt:

- `/health` on every service — Render's health checks cannot send the secret.
- `POST /orders/stripe/webhook` — verified by Stripe signature instead.
- The `/orders` WebSocket namespace — browsers connect directly and cannot hold a
  shared secret, so `OrderGateway.handleConnection` verifies the user's JWT itself.

The guard **fails closed**: if `INTERNAL_API_SECRET` is missing while
`NODE_ENV=production`, the service rejects all traffic rather than serving
unauthenticated requests. Locally, where the variable is usually unset, the guard
stays inert so nothing changes for development.

## Free-plan trade-offs

The blueprint uses `plan: free` throughout. Worth knowing:

- Free instances **spin down after 15 minutes idle** and take ~50 seconds to wake.
  A cold page load can wake several services at once, so the first request after a
  quiet period is slow.
- Free instances share a **750 instance-hour/month** pool across the account. Eight
  always-on services would exhaust it; spin-down is what keeps this viable.
- WebSocket connections to a sleeping order-service fail until it wakes.

For a demo that stays responsive, upgrade `snapbite-frontend`, `snapbite-gateway`,
and `snapbite-order` to `starter` and leave the rest free — change `plan:` in
[render.yaml](render.yaml).

## Running the same images locally

[docker-compose.prod.yml](docker-compose.prod.yml) builds the identical Dockerfiles
with the original private-network topology. It now also needs `INTERNAL_API_SECRET`:

```bash
export JWT_SECRET=... APP_URL=http://localhost INTERNAL_API_SECRET=$(openssl rand -hex 32)
pnpm prod:up
```
